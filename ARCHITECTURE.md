# Архитектура проекта

Документ — источник правды по структуре кода. Правила слоёв проверяются автоматически (`npm run lint:fsd`, линтер [Steiger](https://github.com/feature-sliced/steiger)), остальные — на ревью. Меняя код, обновляйте документацию в том же изменении (§10).

## 1. Принципы

- **Feature-Sliced Design (FSD)**: код делится на слои → слайсы → сегменты; зависимости направлены строго вниз.
- **Data-driven**: конфигуратор — один универсальный движок. Товар описывается данными (опции + матрица SKU), поэтому новый конфигуратор = новый файл данных, а не новый код (см. [docs/adding-a-product.md](docs/adding-a-product.md)).
- **Бизнес-логика — чистые функции** в сегменте `model`, без React и браузерных API; она покрывается юнит-тестами.
- **Простота**: не добавляем абстракции и зависимости «на вырост». Новая зависимость — только с обоснованием в README (раздел «Стек»).

## 2. Слои и направление импортов

Слои сверху вниз. Модуль может импортировать только из слоёв **строго ниже** своего.

| Слой       | Назначение                                                     | В проекте                                                                                  | Слайсы |
| ---------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------ |
| `app`      | Инициализация: точка входа, маршруты, лейаут, глобальные стили | `main.tsx`, `App.tsx`, `routes.tsx`, `Layout.tsx`, `styles/`                               | нет    |
| `pages`    | Экраны, привязанные к маршрутам; собирают виджеты              | `catalog`, `product`, `not-found`                                                          | да     |
| `widgets`  | Самостоятельные крупные блоки интерфейса                       | `site-header`, `site-footer`, `product-gallery`, `product-configurator`, `product-details` | да     |
| `features` | Пользовательские сценарии, приносящие ценность                 | `configure-product`, `add-to-cart`                                                         | да     |
| `entities` | Бизнес-сущности предметной области                             | `product`, `cart`                                                                          | да     |
| `shared`   | Переиспользуемое без бизнес-логики: UI-кит, утилиты, стили     | `ui/`, `lib/`, `config/`, `styles/`                                                        | нет    |

Дополнительные правила:

- **Слайсы одного слоя не импортируют друг друга.** Если нужна общая логика — опускаем её в слой ниже; если нужно объединить — композиция в слое выше (на странице). Пример: галерее, панели опций и деталям нужен один выбранный SKU — состояние живёт в `pages/product`, виджетам передаётся пропсами.
- `app` и `shared` не делятся на слайсы: внутри них сразу сегменты (`shared/ui`, `shared/lib`, …).
- Импорт снизу вверх запрещён всегда (например, `entities` → `features`).

## 3. Слайсы и сегменты

- **Слайс** — папка в `pages|widgets|features|entities`, названная по смыслу предметной области, `kebab-case`: `entities/product`, `features/add-to-cart`.
- **Сегмент** — папка внутри слайса, названная **по назначению**, а не по типу файлов:

| Сегмент  | Что внутри                                           |
| -------- | ---------------------------------------------------- |
| `ui`     | React-компоненты и их стили                          |
| `model`  | Типы, чистая бизнес-логика, хуки состояния, сторы    |
| `api`    | Доступ к данным (здесь — статические данные товаров) |
| `lib`    | Вспомогательные функции слайса                       |
| `config` | Константы и конфигурация слайса                      |

Имена `components`, `hooks`, `types`, `utils`, `helpers` для сегментов запрещены (правило Steiger `fsd/segments-by-purpose`).

Пример слайса:

```
entities/product/
  index.ts          # Public API
  model/            # типы, find-variant.ts, selection.ts, … + *.test.ts
  api/              # catalog.ts, data/*.ts
  ui/               # ProductCard.tsx, ProductCard.module.scss, ProductCard.test.tsx
```

## 4. Public API

- У каждого слайса есть `index.ts` — единственная точка входа. В `shared` слайсов нет, поэтому `index.ts` лежит у каждого модуля внутри сегмента: `shared/ui/icon/index.ts`, `shared/lib/format-price/index.ts`. Снаружи импортируем так: `@/entities/product`, `@/shared/ui/choice-group`; **не** `@/entities/product/model/find-variant` и не `@/shared/ui/choice-group/ChoiceGroup`.
- Внутри слайса — относительные импорты (`../model/types`), и не через собственный `index.ts` (иначе циклы).
- В `index.ts` экспортируем только то, что нужно снаружи. Тесты и стили в Public API не попадают; то, что нужно только тестам слайса (`validateProduct`, `createCartStore`), экспортируется из файла модуля, а тесты импортируют это относительным путём.
- Только именованные экспорты (`export function …`), без `export default`.

## 5. Именование и код

- Папки и модули — `kebab-case` (`find-variant.ts`); React-компоненты — `PascalCase.tsx`; стили — `Component.module.scss`; тесты — рядом с кодом (`*.test.ts`, `*.test.tsx`).
- TypeScript в режиме `strict` (+ `noUncheckedIndexedAccess`), без `any`; типы импортируем только через `import type { X }` — форма `import { type X }` при `verbatimModuleSyntax` оставляет побочный импорт модуля (ESLint это проверяет).
- Props компонентов принимаем как `Readonly<XProps>` (props в React неизменяемы; этого же требует правило SonarLint S6759 в IDE).
- Алиас `@/` указывает на `src/`. Относительные пути выше одного уровня (`../../`) между слоями/слайсами не используем.
- Комментарии — только «почему», а не «что». Тексты интерфейса — на русском.

## 6. Стили

- **SCSS Modules** (`*.module.scss`) для компонентов; глобальные стили только в `app/styles` и `shared/styles`.
- Цвета, отступы, шрифты — только из токенов (CSS custom properties) в `shared/styles/_tokens.scss`. Хардкод цветов в компонентах запрещён. Единственное исключение — цвет свотча отделки: он приходит из данных товара и ставится инлайном (`style={{ backgroundColor }}`).
- Тема — **только светлая**. Токены повторяют палитру centersvet.ru (монохром, Montserrat 300). Скруглены одним радиусом `--radius-panel` (как плашки на страницах товаров сайта: 5px на мобильных, 10px от 900px): серые плашки блоков деталей (их общая подложка — миксин `panel` из `shared/styles/_mixins.scss`), рамка слайдера и превью под ним, блоки опций (`ChoiceGroup`); блок цены повторяет собственные скругления сайта.
- Блоки деталей (`widgets/product-details`), блок цены (`widgets/product-configurator`), шапка (`widgets/site-header`) и подвал (`widgets/site-footer`) повторяют вёрстку centersvet.ru. Размеры, отступы и цвета сняты с живой страницы (стили сайта: `.price-block`, `.amount-controller`, `.page-header`, `.p-footer` и т. д.); при изменении этих блоков сверяйтесь с сайтом, а не подбирайте «на глаз».
- **Контейнер страниц общий**: шапка, страницы (`m.container`) и подвал берут ширину и поля из токенов `--container-max` / `--container-gutter` (как `.container` сайта: поля 15px на телефонах, 30px на планшетах, 3% на десктопе; шире 1880px не растёт). Поля шапки до 1024px — 15px, как у шапки сайта. Высота шапки — токен `--header-height` (75px от 1024px, 51px ниже): на неё опираются sticky-блоки под шапкой (галерея). Зазор между колонками страницы товара равен полям страницы (`column-gap: var(--container-gutter)`): от ширины правой колонки зависит ступень блока цены (крупная — от 540px), и при таком зазоре порог приходится на окно ~1410px, а на экране 1440px (1425px с полосой прокрутки) блок остаётся крупным. Меняя поля, зазор или пропорции колонок, проверяйте ширину колонки на 1400–1440px. Ступени шапки и подвала — миксин `up` с ключами `tablet` (768px), `desktop` (1024px, полная шапка вместо кнопки меню) и `wide` (1440px); полноэкранная галерея добавляет `xl` (1280px), `2xl` (1920px) и `3xl` (2560px).
- Цвета подвала (чёрный фон, серые разделители и «плюс», приглушённый копирайт) — токены `--color-footer-*`; фокус на чёрном — белое кольцо, оно задаётся в стилях подвала.
- Без `!important`; вложенность селекторов — не глубже трёх уровней; адаптив — миксинами из `shared/styles/_mixins.scss`.
- Стили сторонних библиотек (Swiper) подключаем в компоненте-обёртке; внешний вид настраиваем CSS-переменными библиотеки и своими классами.
- **Адаптив компонента по ширине его блока, а не экрана** — container queries: контейнер (`container: имя / inline-size`) объявляет виджет, ступени (`@container имя (min-width: …)`) пишутся в его же стилях. Так сделан блок цены (`widgets/product-configurator`): он живёт в узкой колонке, и размеры должны зависеть от ширины колонки. Компоненты нижних слоёв внутри такого блока (`StockStatus`, `AddToCart`) контейнера не знают: размеры им передаются CSS-переменными с разумными значениями по умолчанию (`--stock-dot-size`, `--order-step-size` и т. п.; список — в начале их `.module.scss`), а виджет переопределяет их по ступеням. Положение компонента относительно соседей задаёт родитель через `className`.
- Правила View Transitions (псевдоэлементы `::view-transition-*`) глобальны по природе и лежат в `shared/styles/_view-transitions.scss`; имя слоя (`view-transition-name`) задаёт компонент, который переходит (`widgets/product-gallery`). Анимации по умолчанию отключаем у `root`, чтобы не затухала вся страница.

## 7. Данные и состояние

- Данные товаров — статические модули `entities/product/api/data/*.ts`. Снаружи доступ только через Public API слайса (`getProductBySlug`, `listProducts`).
- Целостность данных проверяет `validateProduct` (тест каталога прогоняет все товары) — при добавлении товара тест защищает от пропущенных SKU, дублей и битых адресов медиа.
- **Выбор опций хранится в URL** (search params): это источник правды для шаринга ссылки и истории браузера. Пустой URL = дефолтный SKU. Логика — в `features/configure-product` (`useProductConfigurator`), выбор SKU и подбор ближайшей комбинации — чистые функции `entities/product/model`.
- **Маршруты** описаны в `app/routes.tsx`. Страница получает товар из loader маршрута (`pages/product/model/product-loader.ts`): неизвестный slug — ответ 404, который показывает `errorElement`, а не исключение в рендере. `shouldRevalidate` не даёт loader'у перезапускаться при смене опций (меняются только параметры запроса).
- **Галерея показывает только выбранный SKU**: `buildGallerySlides(product, variant)` (`entities/product/model`) собирает его фото, чертёж и общие слайды товара (`extraMedia`); превью строятся из тех же слайдов, поэтому «чужих» кадров (других цветов, чертежа другого трека) в галерее нет. Слайды — слоты (`photo`, `diagram`, id из `extraMedia`), а не SKU: при смене выбора ключи слайдов не меняются, Swiper не пересоздаётся и активный слайд сохраняется. Слайдер не знает о выборе и не меняет его: связь односторонняя — `variant → слайды`; `photo` и `diagram` зарезервированы в `extraMedia` (проверяет `validateProduct`). Фото и чертёж выбранного SKU показываются только в галерее: блок деталей (`widgets/product-details`) их не повторяет — справа от таблицы характеристик в нём стоит блок скачивания (паспорт).
- **Анимация смены кадра** — нативный View Transitions API, а не код слайдера: `useProductConfigurator` передаёт роутеру `viewTransition: canUseViewTransition()` (`shared/lib/can-use-view-transition`: API есть и нет `prefers-reduced-motion`), блок галереи — отдельный слой перехода (`view-transition-name: product-gallery`), глобальные правила — `shared/styles/_view-transitions.scss`. Корневой слой не анимируется — затухает только галерея. Опцию `viewTransition` понимает только data router (`createBrowserRouter`). Фото и чертежи остальных SKU подгружает `shared/lib/preload-image`, чтобы новый кадр уже был в кеше. Слайдер — только готовая библиотека (Swiper) через тонкую обёртку `shared/ui/media-slider`; собственные слайдеры и собственные анимации смены кадра не пишем.
- **Слайдер и полноэкранная галерея** (`shared/ui/media-slider`) повторяют слайдер centersvet.ru на Swiper: горизонтальная прокрутка 600 мс `ease-in-out`, зацикливание (`loop` Swiper 14 переставляет слайды, дубликатов нет), зоны перелистывания по краям кадра (кнопки по 30 % ширины с 768px, стрелка проявляется при наведении; нижняя полоса свободна для управления видео), свайп (мышью не листаем: `simulateTouch: false`), скруглённые рамка и миниатюры; чёрточек-индикаторов нет. Нажатие на кадр картинки (`<button>` «Открыть на весь экран») открывает `MediaLightbox` — второй экземпляр Swiper в нативном `<dialog>`: `showModal()` даёт фокус внутри, Esc, возврат фокуса и неактивную страницу, а прокрутка страницы под ним блокируется CSS `html:has(dialog[open])` без сброса позиции. Размеры и позиции галереи сняты с сайта (`xl`/`2xl`/`3xl` в миксине `up`, токен `--color-lightbox-bg`). Диалог монтируется только открытым, а Swiper — уже после `showModal()` (в закрытом диалоге у слайдера нулевые размеры); **диалог не закрывается в очистке эффекта**: в StrictMode событие `close` пришло бы уже после повторной подписки и закрыло бы галерею. Фокус при открытии отдаётся самому диалогу (`tabIndex={-1}`), а не крестику, который `showModal()` фокусирует по умолчанию: после нажатия клавиши браузер показывает рамку фокуса на сфокусированном элементе, и ←/→ подсвечивали бы крестик; по той же причине нажатие мышью по стрелкам не забирает фокус (`onMouseDown` с `preventDefault`), а Tab по-прежнему доходит до крестика и стрелок. Оба слайдера собирают слайд общим `SlideMedia`; номер слайда при `loop` берём из `realIndex`, а не из `activeIndex` (он смещён перестановкой слайдов).
- **Видео**: файл (`kind: 'video'`) играет тег `<video>`; плеер стороннего сервиса (`kind: 'embed'`, Kinescope) подключается по нажатию на постер (`EmbedPlayer`) и сбрасывается к постеру при уходе со слайда — iframe не играет в фоне и не грузится без запроса.
- Единственное глобальное состояние — корзина (`entities/cart`): внешний стор + `useSyncExternalStore`, персист в `localStorage`. Всё остальное — локальное состояние компонентов или URL. Остаток (`stock`) — граница для корзины: стор не принимает больше остатка с учётом уже лежащего; количество в `features/add-to-cart` ограничено тем же (остаток минус то, что уже в корзине).
- **Наличие** показывается по правилам сайта (`entities/product/model/stock.ts`): от 50 шт. — «В наличии N шт», 1–49 — «В наличии менее 50 шт» (точное число не раскрываем), 0 — «Нет в наличии» и отключённая покупка. Пороги и формулировки меняются только там, а не в компонентах.
- **Цена считается и показывается только в блоке цены** (`widgets/product-configurator`) и при добавлении в корзину (`features/add-to-cart`). Опции (`OptionPicker`) цен и надбавок не показывают: `getOptionValueStates` отдаёт только наличие значения, а разницу цен между значениями нигде не считаем.
- Фото, чертежи и видео-файл — абсолютные URL CDN сайта (`cdn.centrsvet.ru`, hotlink), файлы в репозиторий не копируются; видео-плеер — Kinescope (iframe).
- **Ссылок на сайт и во внешние сервисы нет.** Всё, что на centersvet.ru ведёт наружу (меню и значки шапки, пункты подвала вместе с соцсетями и вакансиями, строка паспорта в блоке скачивания), в прототипе — ссылка-заглушка: компонент `StubLink` (`shared/ui/stub-link`) выводит `<a>` без `href`, который выглядит как ссылка, но не переходит, не открывает вкладок и не получает фокус. В данных адресов нет: у пунктов подвала и меню только названия (`widgets/site-footer/config/footer-rows.ts`, `widgets/site-header/config/menu.ts`), у файла (`ProductFile`) — признак `available`. Настоящие ссылки — только внутренние (логотип, карточки каталога, ссылка на каталог на странице 404), их строит роутер; тест `app/routes.test.tsx` проверяет, что ни на одной странице нет другого `href`. Своя логика у шапки одна — счётчик корзины; состав подвала — данные, а не разметка в компоненте.

## 8. Тесты

- Vitest + Testing Library + jsdom, запуск: `npm test`. Сеть в тестах не используется.
- Обязательно: каждая функция в `model` — юнит-тестом. UI — пользовательскими сценариями (поиск по ролям/aria: `getByRole`, `getByText`), а не по деталям реализации. Интеграция — тесты страниц.
- Тест лежит рядом с модулем. Snapshot-тесты не используем.
- Браузерные API, которых нет в jsdom, мокаются в `test/setup.ts` (глобально) или внутри теста (локально). В jsdom нет вёрстки: размеры элементов нулевые, и Swiper считает слайдер «уже в конце» — поэтому `test/setup.ts` эмулирует размер кадра 800×450. Там же — заглушки `showModal()` и `close()` у `<dialog>` (в jsdom у него только атрибут `open`; событие `close` приходит отложенно, как в браузере). Слайдеры тестируются в режиме «уменьшить движение» (подмена `matchMedia` в самом тесте): jsdom не воспроизводит CSS-переходы, а при `loop` Swiper не принимает новый переход, пока не закончился прежний. Клавиши для модуля `Keyboard` шлём `fireEvent.keyDown(document, { keyCode })`: модуль читает устаревшее `keyCode`, которое `user-event` не заполняет.
- Фикстуры, нужные только тестам модели (`entities/product/model/test-product.ts`), лежат рядом с кодом, не экспортируются из Public API и исключены из покрытия. Тесты UI и страниц используют реальные данные каталога через Public API.
- Страницы с loader'ом рендерятся роутером асинхронно: в тестах ждём появления содержимого (`findBy…`, `waitFor`), а не флага состояния роутера.
- Опцию `viewTransition` роутера понимает только data router: тесты на неё используют `createMemoryRouter` + `RouterProvider` и подставляют `document.startViewTransition` (в jsdom его нет). Без подмены роутер не должен писать предупреждения в консоль — это тоже проверено.
- Плеер и видео в галерее тестируются пользовательскими сценариями (постер → iframe по нажатию, возврат к постеру при уходе со слайда, пауза `<video>` при смене слайда); сеть и воспроизведение не нужны.

## 9. Проверки качества и отступления

`npm run check` = типы (`tsc -b`) + ESLint + Steiger + Vitest + сборка. Команда должна проходить перед каждым коммитом.

Отступления от стандартных правил (всё остальное — по умолчанию):

| Отступление                                       | Причина                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fsd/insignificant-slice` выключено целиком       | Слайсы выделены заранее по роли, а не по числу потребителей: каждый новый конфигуратор переиспользует те же виджеты, фичи и сущности. Частичное отключение (только `widgets/**`, `features/**`) исключает их файлы из подсчёта ссылок и даёт ложные ошибки на `entities`. |
| `fsd/public-api` выключено для `shared/styles/**` | Сегмент состоит из SCSS-partial-файлов без TS-кода; стили подключаются через `@use '@/shared/styles/…'`.                                                                                                                                                                  |

Любое новое отступление записывается сюда вместе с причиной.

## 10. Документация — часть изменения

Документация не должна отставать от кода. Если меняется поведение, публичный API, конфигурация, структура проекта, зависимости или скрипты — **документ обновляется в том же изменении (коммите)**, что и код. «Потом допишу» не принимается.

| Что изменилось                                  | Что обновить                                       |
| ----------------------------------------------- | -------------------------------------------------- |
| Поведение для пользователя, возможности         | `README.md` (раздел «Возможности»)                 |
| Скрипты, зависимости, версии, требования к Node | `README.md` («Стек», «Скрипты»)                    |
| Структура папок, слои, слайсы, правила импортов | `ARCHITECTURE.md` и дерево в `README.md`           |
| Модель данных товара, процесс добавления товара | `docs/adding-a-product.md`, `README.md` («Данные») |
| Отступление от правил архитектуры               | `ARCHITECTURE.md`, §9                              |
| Источники данных, допущения, ограничения        | `README.md` («Данные и допущения»)                 |

Definition of Done для любого изменения:

1. `npm run check` проходит.
2. Новая/изменённая логика покрыта тестами (§8).
3. Документация из таблицы выше обновлена и не противоречит коду.
4. Public API слайсов (`index.ts`) содержит только нужное снаружи.

`CLAUDE.md` — локальный файл с инструкциями для агента: он в `.gitignore` и в репозиторий не попадает. Поэтому правила процесса живут здесь, в `ARCHITECTURE.md`.
